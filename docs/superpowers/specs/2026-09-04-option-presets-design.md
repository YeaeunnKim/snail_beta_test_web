# 옵션 프리셋 — 설계

작성 2026-09-04. 대상: `snail_beta_test_web` + `snail_backend_specification`.

## 1. 배경

옵션 관리(`src/app/dashboard/designs/page.tsx`의 `OptionManager`)에 지금 없는 것 셋:

1. 샵/폴더 단위 옵션 **일괄삭제** (디자인 단위는 있음)
2. 프리셋 옵션의 **가격·소요시간을 등록 전에 정하고, 등록 후에 고치면 이미 깔린 디자인에도 반영**
3. 일괄등록 **덮어쓰기 모드** (현재는 `옵션 0개인 것만` / `전체에 추가(중복)` 둘뿐)

현재 프리셋 7개는 `design-settings.tsx`의 `COMMON_OPTION_PRESETS`에 이름·종류만 상수로 박혀 있고,
가격·시간은 `OPTION_PRICE_DEFAULT` / `OPTION_DURATION_DEFAULT` 고정값으로 등록된다.

## 2. 핵심 결정

### 2.1 부모↔자식 연결선을 서버에 둔다 (컬럼 2개)

요구사항의 *"걔를 수정하면 해당 옵션 적용된 디자인들의 옵션도 일괄 수정"* 은 **정체성 관계**다.
(종류+이름) 문자열 매칭으로 흉내내면 세 군데서 깨진다.

- 어느 디자인에서 옵션 이름을 고치면 그 자식이 조용히 이탈한다
- 손으로 만든 동명 옵션과 프리셋에서 온 옵션을 구분 못 해 남의 값을 덮어쓴다
- "프리셋에서 온 것만 일괄삭제"가 불가능하다

그래서 `design_options`에 연결선 컬럼을 둔다.

### 2.2 정식 템플릿 테이블(+FK)이 아니라 컬럼으로 간다

베타웹 구현은 실험이고, 운영자웹에 넣을 때는 처음부터 재설계할 계획이다(사용자 확인).
그 전제에서 판단 기준은 "제일 견고한 안"이 아니라 **되돌리기 비용**이다.

| | 컬럼 안(채택) | 정식 테이블 안 |
|---|---|---|
| 기능 | 동일 | 동일 |
| 접을 때 | nullable 컬럼 2개 방치 | 테이블·라우터·마이그레이션이 체인 중간에 잔재 |
| 계약 재생성 | 필드 2개 | 신규 경로 4~6개 |
| 프리셋 삭제 정책 | 고아 키로 남김(제약 없음) | `CASCADE`/`SET NULL`/`RESTRICT` 강제 선택 |

옵션 관리 UI는 **베타웹에만 있다**(운영자웹 `dashboard/designs/`엔 `page.tsx`뿐, `design-settings.tsx` 없음).
정식 테이블을 파면 진짜 제품에 소비자 없는 스키마가 생긴다.

### 2.3 연결 키는 이름이 아니라 uuid

`"removal:자샵제거"` 같은 파생 키는 프리셋 쪽 이름을 고치면 끊긴다.
프리셋 옵션 생성 시 uuid를 한 번 발급해 고정한다. 프리셋 이름·옵션 이름·가격 무엇을 바꿔도 연결이 유지된다.

### 2.4 전파는 "기본은 보존, 덮기는 선택"

이 repo는 견적서에서 반대 결정을 한 적이 있다 — `shop_quote_templates` 마이그레이션 주석:
*"렌더된 결과는 `reservation_requests.quote_text`에 생성 시점 스냅샷으로 저장"* (= 전파 안 함).
여기서는 의도적으로 전파하되, **개별 조정된 값은 기본 보존하고 사장님이 체크해야 덮는다.**

옛 프리셋 값이 서버에 있으므로 "안 건드린 자식"과 "손으로 조정한 자식"을 정확히 가를 수 있다.

## 3. 데이터 모델

마이그레이션 1파일, 컬럼 2개. 새 테이블·새 라우터 없음.

```
shops.option_presets : JSONB | None
[
  { "id": "<uuid>", "name": "기본 세트",
    "options": [
      { "key": "<uuid>", "kind": "removal", "name": "자샵 제거",
        "price_delta": 50000, "duration_delta_min": 30, "sort_order": 0 }
    ] }
]

design_options.template_key : String(64) | None   -- 위 options[].key
                                                  -- 손으로 만든 옵션은 NULL
```

- 프리셋 삭제 시 자식의 `template_key`는 고아로 남는다. JSONB라 FK 제약이 없어 DB가 막지 않는다.
  화면에서 "연결 끊김"으로 표시하고, 일괄 작업 대상에서 제외한다.
- 프리셋당 옵션 상한 20 (`MAX_DESIGN_OPTIONS`와 동일). 샵당 프리셋 상한 10.

### API

**기존 엔드포인트를 그대로 쓴다.** 신규 경로 0개.

- `GET /shops/me` → `option_presets` 읽기
- `PATCH /shops/me` → `option_presets` 저장
- `POST /shops/me/designs/{id}/options` → body에 `template_key` 추가
- `PATCH /shops/me/designs/{id}/options/{oid}` → body에 `template_key` 추가
- `DELETE /shops/me/designs/{id}/options/{oid}` → 그대로
- `DesignOptionPublic` 응답에 `template_key` 추가

앱(iOS)은 `designDetailApi.ts:57`의 `mapOption()`이 필드를 명시적으로 골라 쓰므로 nullable 필드 추가에 안 깨진다.

## 4. 프론트 설계

### 4.1 프리셋 관리 (신규 섹션)

```
프리셋
  기본 세트 (7개)      [수정] [복제] [삭제]
  여름 프로모션 (3개)  [수정] [복제] [삭제]
  + 새 프리셋
```

`수정` → 편집 화면. 프리셋 이름 + 옵션 행(종류·이름·가격·시간·삭제) + `+ 옵션 추가`.
`저장` → `PATCH /shops/me`로 프리셋만 먼저 저장.

값이 바뀐 게 있으면 이어서 전파 확인:

```
  이 프리셋이 적용된 디자인 42개가 있습니다.
    [x] 프리셋과 값이 같던 39개를 새 값으로 갱신
    [ ] 개별 조정된 3개도 덮어쓰기 (8만·8만·4만)
              [아니오, 프리셋만 저장]   [네, 갱신합니다]
```

**시드**: `option_presets`가 비어 있으면 기존 `COMMON_OPTION_PRESETS` 7개를
"기본 세트" 프리셋 1개로 만들어 저장한다(가격·시간은 기존 기본값). 기존 사용자에게 화면이 그대로 보인다.

### 4.2 일괄등록 3모드

범위(샵/폴더/디자인) × **프리셋 선택** × 모드:

| 모드 | 동작 |
|---|---|
| 옵션 0개인 것만 | 기존 유지 |
| 전체에 추가(중복) | 기존 유지 |
| **덮어쓰기**(신규) | `template_key`가 이 프리셋 것인 옵션은 프리셋 현재 값으로 갱신, 없으면 생성. `template_key=NULL`은 안 건드림 |

덮어쓰기는 `MAX_DESIGN_OPTIONS = 20` 초과 문제도 해소한다(중복이 안 쌓임).

### 4.3 일괄삭제

범위(샵/폴더) × 대상:
- **선택한 프리셋에서 온 것만** (`template_key ∈ 프리셋 키들`) — 기본값
- 전부

실행 전 `"디자인 42개에서 옵션 294개가 삭제됩니다"` 미리보기 + 확인. 되돌리기가 없으므로 미리보기는 필수.

### 4.4 초기화 (강한 버튼)

```
[ 이 범위 옵션 전부 삭제하고 프리셋으로 초기화 ]
   폴더 '여름'의 디자인 42개에서 옵션 294개를 전부 삭제하고
   '기본 세트' 7개로 다시 깝니다.
   손으로 만든 옵션 12개도 함께 삭제됩니다. 되돌릴 수 없습니다.
              [아니오]   [네, 초기화합니다]
```

**모든 확인창의 버튼 순서는 `[아니오] [네]`** — 취소가 왼쪽, 확인이 오른쪽으로 통일한다.

### 4.5 실행 방식

전파·삭제·적용은 프론트 순회(벌크 엔드포인트 없음).

- 동시 6개 제한 + 진행률 표시
- 중간 실패해도 나머지 계속. 종료 후 `"294개 중 291개 성공, 3개 실패"` 리포트 + 실패분 재시도
- **사전 검증**: 적용 후 옵션 수가 20을 넘길 디자인이 있으면 실행 전에 막고 대상을 알려준다.
  400을 맞고 알게 되면 이미 절반 적용된 상태가 된다.

## 5. 검증

- 베타웹: `pnpm typecheck && pnpm lint && pnpm build`
- 백엔드: 기존 테스트 + 옵션 서비스 테스트에 `template_key` 왕복 케이스 추가
- 계약: `tools/sync_contract.ps1` — **Python 3.12 venv 필수**
  (`AGENTS.md`: 3.13이면 422 phrase 차이로 CI 드리프트). 히스토리에 재발 이력 다수.
- 베타웹 타입: 백엔드 계약이 GitHub Pages에 published 된 뒤 `pnpm generate:types:remote`

## 6. 순서 의존성

백엔드가 먼저 배포되고 계약이 published 돼야 베타웹 타입 생성이 된다.

```
백엔드 마이그레이션·스키마 → 계약 재생성(3.12) → PR·머지 → 자동배포(deploy.yml)
   → GitHub Pages published 확인
      → 베타웹 generate:types:remote → UI 구현 → PR·머지 → pnpm deploy:main
```

## 7. 나중 재설계로 넘길 것

운영자웹에 제대로 구현할 때 이 베타에서 확인된 것을 입력으로 쓴다.

- 프리셋을 정식 테이블(`shop_option_templates` + `design_options.template_id` FK)로 승격.
  `template_key`(uuid 문자열) → `template_id`(FK) 마이그레이션 한 번이면 된다.
- 전파·일괄삭제를 벌크 엔드포인트로 이관(요청 1번, 전부 되거나 전무).
  프론트는 호출부만 교체된다.
- 프리셋 삭제 시 자식 처리 정책을 DB 제약으로 확정.
- 베타에서 실제로 쓰인 모드/덮어쓰기 빈도를 보고 UI를 줄인다.
